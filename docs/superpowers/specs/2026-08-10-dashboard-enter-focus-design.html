Ganymede · Dashboard

Enter moves focus into the working client

source: docs/superpowers/specs/2026-08-10-dashboard-enter-focus-design.md · generated view for review · canonical: markdown
✓ Design approved ⚠ Not yet implemented

Enter already points the working client at the right Session or repo, but keystrokes stay on the Dashboard until you separately press alt+g. This spec adds a Focus primitive that Enter fires automatically — but only from the direct gestures, never from the async guard fallbacks that must never steal your keystrokes out from under you.

TL;DR
i

Add a `Focus` step that Enter calls after a successful Jump or Open. It runs `select-pane` on the dock server — the same move alt+g makes — so Enter both shows the Session/repo and hands you the keyboard in one gesture.

Applies to session rows, repo rows, and the picker's Enter. Deliberately not applied to the async guard-fallback paths (`answered`/`sent` mismatches, Takeover's `endFailed`, Stop's fallback) — those fire from background events and must not yank focus away from whatever you're doing on the Dashboard.

1 · Why the gap exists

The dock is two tmux panes side by side — the Dashboard and a "working client" that is itself a tmux client attached to a separate server holding the repo Sessions. Enter and alt+g each move a different half of "being in a Session":

What the working client shows
switch-client on the Sessions server. This is what Jump and Open already do — pressing Enter today gets you this far.
Which dock pane has keyboard focus
select-pane on the dock server. This is what alt+g does today, and what Enter has never touched.

Two different tmux servers, two different calls — Enter needs to fire both.

2 · The new pieces

topology.Harness.Focus — new file internal/topology/focus.go, alongside jump.go and open.go's one-action-per-file shape. Targets =dock:0.1, the same pane id ensureDock already selects when the dock is first built.

// Focus moves keyboard focus in the dock to the working client's pane — the // same move alt+g makes, given automatically once a jump or an open has // already put something new in front of you. func (h Harness) Focus() error { return h.dock().run("select-pane", "-t", "="+DockSession+":0.1") }

dashboard.Focuser — sibling interface to Jumper and Opener, added as a field on dashboard.Harness (same "any of them may be absent" contract). Wired in cmd/ganymede/main.go as Focuser: harness — topology.Harness satisfies it structurally, same as it already does for Jumper/Opener.

// Focuser moves keyboard focus to the working client's pane — the dock's own // alt+g, given automatically once Enter has already put something in front // of you. type Focuser interface { Focus() error }
3 · Which Enter paths get it
PathTriggerCalls Focus?Why
jump() → jumpToEnter on a Session row YesDirect, synchronous Enter gesture.
goTo (Dashboard)Enter on a repo row, no live Session yet YesDirect gesture; goTo calls Focus unconditionally after a successful Open.
goTo (picker)Enter in the repo picker YesSame goTo, same direct gesture — free with no extra wiring.
answered mismatch → jumpToGuard could not verify an approve/deny NoAsync background event — may land mid-keystroke on something unrelated.
focusPane (sent / Takeover / Stop)Guard fallbacks that show a pane without marking it seen NoUnchanged — same reasoning that already keeps these from touching Seen.

jumpTo is shared between the first and fourth rows, so it gains a moveFocus bool parameter rather than duplicating the Jump logic:

jump()→jumpTo(s, true)→Focus()
answered mismatch→jumpTo(s, false)→— skipped —

Focus errors are ignored (_ = ...Focus()) — same best-effort treatment as focusPane's own Jump call and popup sweeping elsewhere in this codebase. Nothing actionable to tell the user, and a failed focus-move must not overwrite a successful Jump/Open's own notice.

4 · Testing

A focuses fake (Focus() error, recording calls, settable error) mirrors the existing jumps and opens fakes already in dashboard_test.go.

  • 1Session row Enter calls Jump then Focus.
  • 2Repo row Enter and picker Enter call Open then Focus.
  • 3answered-mismatch fallback calls Jump (via jumpTo) but not Focus.
  • 4focusPane's callers (sent mismatch, Takeover's endFailed, Stop's fallback) call Jump but not Focus — unchanged from today.
5 · Asked & answered
Should Enter auto-focus the working client for repo rows and the picker too, or only for Session rows as originally described?
Both. Repo rows (goTo/Open) and the picker's Enter get Focus too, for consistency with Session rows — Enter should always finish the job it starts, everywhere it's offered.
